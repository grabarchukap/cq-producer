# Мультиагентный Telegram-бот «Мысль → Пост»
## Технический план реализации — v4

> **Назначение документа:** руководство для разработчика. Описывает что строить, из каких компонентов, как они взаимодействуют и почему приняты те или иные решения. Готовый код не является частью плана.

---

## 1. Назначение системы

Бот принимает голосовое сообщение или текст от пользователя, прогоняет его через цепочку AI-агентов и возвращает готовый пост в выбранном стиле (Tone of Voice). После получения результата пользователь может интерактивно редактировать пост через диалог с агентом правки.

Система рассчитана на несколько фиксированных пользователей с контролируемым доступом и управляется через встроенный административный интерфейс.

|-----------|------------|---------|

## 5. Профиль автора

Профиль — единственное место где хранится всё относящееся к конкретному автору: стиль, правила форматирования, примеры постов и промпты агентов. Изменение поведения под конкретного автора не требует правки кода.

### 5.1 Структура профиля

```
{
  "id"               — уникальный slug, только [a-z0-9_], макс. 32 символа
  "display_name"     — отображаемое имя в интерфейсе бота
  "language"         — язык ("ru" / "en")
  "tone_description" — текстовое описание стиля автора
  "forbidden_phrases"— список слов и фраз которые нельзя использовать
  "post_structure"   — правила форматирования поста:
      max_length_chars   — максимум символов
      paragraphs         — допустимое число абзацев
      use_emoji          — разрешены ли эмодзи (bool)
      use_hashtags       — использовать ли хэштеги (bool)
      hashtag_style      — где и как ставить хэштеги
      formatting_hints   — дополнительные указания по структуре
  "agent_prompts"    — скелеты промптов для каждого агента:
      expand, tone, format, qa, edit
  "examples"         — массив примеров постов:
      [ { "post": "текст поста" }, ... ]
}
```

### 5.2 Логика промптов агентов

Каждый агент строит свой системный промпт из двух частей:

- **Скелет** (`agent_prompts.<agent>`) — фиксированная инструкция из профиля. Описывает роль агента и ожидаемый формат ответа. Редактируется в JSON.
- **Контекст** — динамические данные из профиля: `tone_description`, `forbidden_phrases`, `post_structure`, `examples`. Подставляются агентом в коде поверх скелета.

Такое разделение позволяет тюнить поведение агента через JSON не рискуя сломать логику подстановки данных.

### 5.3 Валидация профиля

При загрузке каждый JSON проходит валидацию через Pydantic-схему (`profiles/schema.py`). Профиль с невалидной структурой не загружается — бот логирует ошибку и пропускает файл. Это предотвращает падение пайплайна из-за кривого JSON.

Обязательные поля: `id`, `display_name`, `agent_prompts` (все 5 ключей), `post_structure`.

### 5.4 Кэш профилей

Профили загружаются с диска один раз при старте и хранятся в памяти. Кэш инвалидируется явно — только при создании или удалении профиля через админ-интерфейс. Это исключает лишние I/O на каждый запрос.

## 6. База данных

SQLite-файл создаётся автоматически при первом запуске. Все операции с БД асинхронные через `aiosqlite`.

### 6.1 Таблицы

**`whitelist`** — контроль доступа к боту:
```
user_id    INTEGER PRIMARY KEY   — Telegram user_id
username   TEXT                  — @username (опционально, для читаемости)
added_at   DATETIME              — дата добавления
```

**`posts`** — история сгенерированных постов (не активна на старте):
```
id          INTEGER PRIMARY KEY AUTOINCREMENT
user_id     INTEGER   — кто генерировал
author_id   TEXT      — какой профиль использовался
raw_input   TEXT      — исходный текст/транскрипт
final_post  TEXT      — финальный пост
created_at  DATETIME
```

### 6.2 Операции whitelist

- `is_allowed(user_id)` → bool — проверка доступа
- `add_user(user_id, username)` — добавление
- `remove_user(user_id)` — удаление
- `list_users()` → list — список всех пользователей

### 6.3 Включение истории постов

Таблица `posts` создаётся сразу. Запись в неё заглушена. Для активации: раскомментировать вызов `save_post()` в оркестраторе после завершения пайплайна.

## 7. Агенты

### 7.1 Общие принципы

- Каждый агент — отдельный модуль с одной публичной функцией
- Агент не знает о других агентах — только вход и выход
- Все вызовы LLM обёрнуты в retry с exponential backoff (3 попытки)
- Агент не хранит состояние между вызовами
- Пустой ответ от LLM — исключение, не молчаливый проброс

### 7.2 Агент 1: STT (Speech-to-Text)

**Вход:** байты аудиофайла (OGG из Telegram)  
**Выход:** строка транскрипта  
**Провайдер:** OpenAI Whisper API, модель `whisper-1`, язык `ru`

**Граничные случаи которые нужно обработать:**
- Файл > 25 МБ → отклонить до отправки в API
- Пустой транскрипт (тишина, шум) → выбросить исключение с понятным сообщением пользователю
- Ошибка API → retry, затем исключение

### 7.3 Агент 2: Expand

**Вход:** raw_text (транскрипт или введённый текст), profile  
**Выход:** draft — развёрнутый черновик  
**Промпт:** `profile.agent_prompts.expand`  
**max_tokens:** 600

Задача агента — убрать слова-паразиты, связать мысль в читаемый черновик. Не добавлять идей которых нет во входе.

### 7.4 Агент 3: Tone of Voice

**Вход:** draft, profile  
**Выход:** toned — черновик переписанный в стиле автора  
**Промпт:** скелет из `profile.agent_prompts.tone` + `tone_description` + `forbidden_phrases` + `examples`  
**max_tokens:** 800

Задача — переписать в стиле автора, сохранив все факты. Примеры из профиля идут в системный промпт как блок «примеры постов автора».

### 7.5 Агент 4: Format

**Вход:** toned, profile  
**Выход:** formatted — пост с применённым форматированием  
**Промпт:** скелет из `profile.agent_prompts.format` + все поля `post_structure`  
**max_tokens:** 600

Задача — применить правила платформы: длина, абзацы, эмодзи, хэштеги, структура.

### 7.6 Агент 5: QA

**Вход:** formatted, profile  
**Выход:** final_post — проверенный и при необходимости исправленный пост  
**Промпт:** скелет из `profile.agent_prompts.qa` + `tone_description` + `forbidden_phrases` + правила `post_structure`  
**max_tokens:** 700

Задача — финальная проверка: орфография, соответствие стилю, запрещённые фразы, длина. Если всё ок — вернуть без изменений.

### 7.7 Агент 6: Edit (интерактивная правка)

**Вход:** current_post (текущая версия поста), user_request (запрос на правку), profile  
**Выход:** new_post — обновлённая версия поста  
**Промпт:** скелет из `profile.agent_prompts.edit` + `tone_description`  
**max_tokens:** 800

Задача — внести только запрошенные изменения, сохранив стиль. Не запускает полный пайплайн — только точечная правка.

**Важно:** `current_post` всегда передаётся целиком. Агент не имеет доступа к истории правок — только к текущей версии и текущему запросу. Это осознанное решение: дешевле по токенам, достаточно для задачи.

## 8. Оркестратор

Управляет последовательным запуском агентов 1–5. Не знает о Telegram — принимает данные, возвращает результат.

**Интерфейс:**
```
run_pipeline(
    audio_bytes: bytes | None,
    text: str | None,
    author_id: str,
    on_progress: async callable | None
) → str (финальный пост)
```

**Последовательность:**
1. STT (если audio_bytes) или sanitize (если text)
2. Валидация: пустой ввод после STT → исключение с понятным сообщением
3. Expand → draft
4. Tone → toned
5. Format → formatted
6. QA → final_post
7. Опционально: save_post() (заглушка)

**on_progress** — async-колбэк, вызывается перед каждым шагом. Используется ботом для обновления статусного сообщения. Если не передан — игнорируется.

## 9. Контроль доступа

### 9.1 Whitelist

Все пользовательские хендлеры защищены декоратором `@require_auth`. Декоратор делает async-запрос в БД и отклоняет неавторизованных пользователей. Хранится в SQLite — добавление/удаление без перезапуска бота.

### 9.2 Административный интерфейс

Команда `/admin`. Доступна любому пользователю Telegram, но требует пароль при каждом входе. Пароль — строка из `.env`, сравнивается напрямую. После верного ввода сессия считается авторизованной до следующего `/admin` или перезапуска бота.

**Важно:** сообщение с паролем нигде не логируется.

### 9.3 Изоляция режимов

Пользовательские и административные состояния хранятся раздельно в `context.user_data`. Роутер в `bot/router.py` направляет входящее сообщение либо в пользовательский хендлер, либо в административный — на основе активного состояния сессии.

## 10. FSM (управление состояниями)

Состояния хранятся в `context.user_data` — словаре python-telegram-bot, привязанном к пользователю.

### 10.1 Пользовательские состояния

| Состояние | Описание |
|-----------|---------|
| `IDLE` | Ожидание ввода |
| `PROCESSING` | Пайплайн в процессе |
| `EDITING` | Режим интерактивной правки |

**Правило сброса:** команда `/start` всегда сбрасывает состояние в `IDLE` и очищает `current_post`. Это защищает от застревания в состоянии после перезапуска бота.

### 10.2 Административные состояния

| Состояние | Описание |
|-----------|---------|
| `IDLE` | Не в режиме админа |
| `AWAIT_PASSWORD` | Ожидание ввода пароля |
| `MENU` | Главное меню, ожидание выбора |
| `AWAIT_TOV_NAME` | Ввод имени нового профиля |
| `AWAIT_TOV_STYLE` | Ввод описания стиля |
| `AWAIT_EXAMPLE` | Ожидание текста примера поста |
| `SELECT_DELETE_TOV` | Выбор профиля для удаления |
| `SELECT_DEL_EXAMPLE` | Выбор примера для удаления |
| `AWAIT_ADD_USER` | Ввод user_id для добавления |
| `AWAIT_DEL_USER` | Ввод user_id для удаления |

## 11. Пользовательский флоу

### 11.1 Старт и выбор ToV

1. `/start` → сброс состояния → список профилей авторов (inline keyboard)
2. Пользователь выбирает автора → `author_id` сохраняется в сессии → подтверждение
3. Бот готов к приёму ввода

Выбор ToV — свободный при каждом сеансе. Привязки пользователя к конкретному автору нет.

### 11.2 Генерация поста

1. Пользователь отправляет голосовое или текст
2. Если `state == PROCESSING` → сообщение «подожди» → игнор
3. `state = PROCESSING` → статусное сообщение «⏳ Начинаю...»
4. Оркестратор запускает пайплайн, обновляет статус на каждом шаге
5. Успех → `state = IDLE` → статус меняется на «✅ Готово!» → пост с кнопками [✏️ Редактировать] [✅ Готово]
6. Ошибка → `state = IDLE` → статус меняется на сообщение об ошибке

### 11.3 Режим правки

1. Кнопка «✏️ Редактировать» → `state = EDITING` → запрос на правку
2. Пользователь отправляет текст или голосовое с правкой
3. Голосовое в режиме EDITING → расшифровка → правка
4. Агент 6 применяет правку → новая версия поста с кнопками [✏️ Ещё правка] [✅ Готово]
5. Кнопка «✅ Готово» → `state = IDLE` → `current_post = None` → сообщение завершения

## 12. Административный флоу

### 12.1 Вход

1. `/admin` → `admin_state = AWAIT_PASSWORD` → запрос пароля
2. Пароль верный → `admin_authed = True`, `admin_state = MENU` → главное меню
3. Пароль неверный → сообщение об ошибке, остаёмся в `AWAIT_PASSWORD`

### 12.2 Управление профилями ToV

**Добавить ToV:**
1. Ввод отображаемого имени → `id` генерируется автоматически (slug из имени)
2. Ввод описания стиля
3. Профиль создаётся из `_template.json` с подставленными данными
4. Примеры добавляются отдельно через «Добавить пример»

**Удалить ToV:**
1. Список профилей → выбор → подтверждение → полное удаление файла
2. Кэш профилей инвалидируется немедленно

### 12.3 Управление примерами

**Добавить пример:**
1. Выбор автора → отправка текста поста
2. Текст добавляется в массив `examples` профиля, файл перезаписывается
3. Кэш инвалидируется

**Удалить пример:**
1. Выбор автора → список примеров (первые 40 символов каждого) → выбор → удаление
2. Файл перезаписывается, кэш инвалидируется

### 12.4 Управление whitelist

**Добавить пользователя:**
1. Ввод Telegram user_id (числовой) → валидация что это число → запись в БД

**Удалить пользователя:**
1. Показать список текущих пользователей → ввод user_id → удаление из БД

## 13. Роутинг сообщений

Все входящие текстовые сообщения проходят через центральный роутер (`bot/router.py`). Роутер проверяет активные состояния сессии и направляет сообщение в нужный хендлер.

**Порядок проверки:**
1. Если `admin_state` активен и не `IDLE` → `admin.on_message()`
2. Если `user_state == EDITING` → `handlers.on_edit()`
3. Если `user_state == PROCESSING` → «подожди» и выход
4. Иначе → `handlers.on_input()`

Такой единый роутер исключает коллизии когда одно сообщение могут перехватить несколько хендлеров.

## 14. Обработка ошибок

### 14.1 Принципы

- Каждый агент оборачивает вызов LLM в `try/except` с retry
- Ошибки API с кодом 4xx (кроме 429) не повторяются
- Ошибки 5xx и 429 повторяются с backoff: 0.5s → 1s → 2s
- После 3 неудачных попыток исключение поднимается в оркестратор
- Оркестратор ловит все исключения и возвращает понятное сообщение пользователю
- Состояние `PROCESSING` сбрасывается в `IDLE` в блоке `finally`

### 14.2 Граничные случаи

| Ситуация | Поведение |
|---------|----------|
| Пустой транскрипт от Whisper | Исключение «Не удалось распознать речь — попробуй ещё раз» |
| Аудио > 25 МБ | Исключение до вызова API «Файл слишком большой» |
| Несуществующий `author_id` | Исключение в `get_profile()`, ловится в оркестраторе |
| Пустой ответ от Claude | Исключение в агенте |
| Перезапуск бота в момент PROCESSING | `/start` сбрасывает состояние при следующем обращении |
| Двойной запрос в PROCESSING | Игнорируется с сообщением пользователю |

## 15. Безопасность

| Угроза | Решение |
|--------|---------|
| Несанкционированный доступ | Whitelist в SQLite, `@require_auth` на всех пользовательских хендлерах |
| Брутфорс пароля админки | Пароль из `.env` (длинный, случайный), вводится при каждом входе |
| API-ключи в коде | Только в `.env`, файл в `.gitignore` |
| Prompt injection через ввод | `sanitize()` на всех текстовых входах: очистка HTML-тегов и LLM-разделителей |
| Слишком длинный ввод | Лимит 4 000 символов в `sanitize()`, дополнительная проверка в `llm.py` (макс. 8 000 до Claude) |
| Аудио большого размера | Проверка размера до вызова Whisper API |
| Утечка профилей | Клиенту передаются только `id` и `display_name` |
| Пароль в логах | Сообщение с паролем не логируется нигде в цепочке |
| Инъекция через `author_id` | `id` в профиле валидируется regex `[a-z0-9_]`, slug генерируется автоматически |
| Параллельный запуск пайплайна | Блокировка через проверку `state == PROCESSING` |

## 16. Оценка стоимости

### Токены на один пост

| Агент | Вход (ср.) | Выход (ср.) |
|-------|-----------|------------|
| Expand | 250 | 400 |
| Tone | 700 | 500 |
| Format | 550 | 450 |
| QA | 500 | 450 |
| **Итого** | **2 000** | **1 800** |

**Стоимость** (claude-sonnet-4: $3/1M input, $15/1M output):  
~$0.033 за пост (~3 руб.)

**Одна итерация правки** (Агент 6): ~1 400 токенов → ~$0.018 (~1.7 руб.)

**STT** (Whisper): ~$0.006 за минуту аудио

### Оптимизации (заложены в архитектуру)

1. Нет истории диалога между агентами — каждый получает только нужный контекст
2. `max_tokens` ограничен индивидуально для каждого агента
3. Кэш профилей в памяти — диск читается только при изменениях
4. STT через Whisper, не через Claude — дешевле в 8-10 раз
5. Агент Edit не перезапускает полный пайплайн
6. Примеры в профиле — только текст поста, без лишних полей
7. При необходимости Expand+Tone можно объединить в один агент — экономия ~600 токенов

## 17. Масштабируемость

Текущая архитектура рассчитана на несколько пользователей. При росте нагрузки:

- **SQLite → PostgreSQL:** заменить `aiosqlite` на `asyncpg`, схема таблиц не меняется
- **Профили в файлах → БД:** `profiles/loader.py` — единственное место замены, интерфейс `get_profile()` / `list_profiles()` не меняется
- **Polling → Webhook:** замена `run_polling()` на `run_webhook()` в `main.py`
- **Добавление автора:** создать JSON по шаблону — код не трогать

## 18. Деплой

### Локальный запуск

```
1. Клонировать репозиторий
2. Создать виртуальное окружение: python -m venv .venv
3. Установить зависимости: pip install -r requirements.txt
4. Скопировать .env.example → .env, заполнить все переменные
5. Запустить: python main.py
```

### Продакшн (Railway / Render / VPS)

- Тип процесса: `worker` (не web — webhook не нужен для polling)
- Переменные из `.env` добавить в дашборд платформы, не коммитить файл
- `storage/posts.db` не сохраняется между деплоями на Railway/Render без persistent volume. Решение: подключить volume или перейти на PostgreSQL при необходимости постоянного хранения

### Первый запуск

При старте приложение:
1. Инициализирует БД (создаёт таблицы если их нет)
2. Загружает и валидирует все профили из `profiles/authors/`
3. Запускает polling
